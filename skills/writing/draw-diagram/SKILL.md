# 다이어그램 작성 (draw-diagram)

이 파일은 길잡이다. 규칙 본문은 `references/` 아래에 계층별로 나뉘어 있고, 지금 그리는 그림에 필요한 파일만 읽는다.

## 계층과 우선순위

```
references/core.md              0층  모든 다이어그램
references/types/<type>.md      1층  구조도 / 흐름도
references/modules/<module>.md  가로축  출력 도구와 부가 기능
assets/                         스타일 원본 (복사해서 씀)
```

- 읽는 순서: core → type → 모듈
- 같은 항목에서 규칙이 부딪치면 type이 core를 이긴다
- 모듈은 2절 도구 선택에서 정해진 것만 읽는다

## 1. 분류

| type | 답하는 질문 | 예 | 읽을 파일 |
|---|---|---|---|
| 구조도 | 무엇이 무엇으로 이루어지나 | 모델 아키텍처, 블록 내부, 모듈 구성 | `types/structure.md` |
| 흐름도 | 어떤 순서로 무엇이 일어나나 | 학습 단계, 데이터 파이프라인, 에이전트 제어 흐름, 샘플링 절차 | `types/flow.md` |

- 한 그림에 두 type이 다 필요하면 패널로 나누고, 패널마다 해당 type 규칙을 적용한다.
- 값을 보여주는 그림(막대·선 그래프, 히트맵 수치)은 범위 밖이다. 데이터 시각화 스킬로 넘긴다.
- 애매하면 "이 그림이 답하는 질문"을 기준으로 정하고, 그래도 애매하면 AskUserQuestion으로 묻는다.

## 2. 도구 선택

| 그림이 들어갈 곳 | 도구 | 모듈 |
|---|---|---|
| LaTeX 문서 | TikZ | `modules/tikz.md` |
| HTML 문서 | 인라인 SVG | `modules/svg.md` |
| Markdown 문서 | 이미지 파일(SVG, 필요하면 PNG) + md 링크. 소스는 수식 기호가 있으면 TikZ, 없으면 SVG | `modules/markdown.md` + 소스 도구 모듈 |

- LaTeX 문서에 들어가면 묻지 않고 TikZ를 쓴다.
- 들어갈 곳이 분명하면 묻지 않고 그 도구를 쓴다.
- 들어갈 곳이 정해지지 않았거나 두 도구가 다 가능하면 AskUserQuestion으로 묻는다. 선택지마다 결과물 형태(TikZ → .tex + PDF/PNG, SVG → .svg 또는 HTML 삽입)를 함께 적는다.
- 데이터 내용물 그림(스켈레톤, 파형, 지도, 썸네일)이 들어가면 `modules/content-images.md`를 추가로 읽는다.

## 3. 규칙 로드

1. `references/core.md`를 끝까지 읽는다.
2. type 파일을 읽는다.
3. 2절에서 정한 모듈 파일을 읽는다.
4. 작업 목록 첫 항목에 적용 규칙을 적는다. 예: "core + 구조도 / 모듈: TikZ, 내용물 그림"

## 4. 절차

1. 분류
2. 도구 선택
3. 규칙 로드
4. 요소표 작성: 노드(이름·모양·색), 그룹, 화살표마다 뜻, 색 배정, 흐름 방향. 단독 요청이면 사용자에게 보여주고 확인받은 뒤 그린다. write-docs 같은 문서 스킬 안에서 호출되면 그 문서의 합의를 따른다.
5. 그림
6. 검증: core 점검 + type 점검 + 사용한 모듈의 점검. 렌더링 결과를 직접 본다.
7. 전달: 소스 파일, 렌더링 결과, 캡션 초안. 캡션에서 그림 속 기호와 칩의 뜻을 정의한다.

## 새 type·모듈 추가

- 새 그림 종류는 `references/types/`에 파일 하나로 추가하고, 1절 표에 한 줄을 더한다.
- 새 출력 도구는 `references/modules/`에 추가하고, 2절 표에 한 줄을 더한다.
- 두 type이 같은 규칙을 갖게 되면 core로 올린다.
- 사용자가 직접 지적한 문제 중 일반적인 것은 해당 계층의 규칙으로 추가하자고 제안한다.
