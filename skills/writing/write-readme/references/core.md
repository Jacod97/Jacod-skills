# README 공통 규칙

## 목적과 독자

- README는 프로젝트 소개와 사용 안내를 제공한다. 소스 코드 요약으로 만들지 않는다.
- 프로젝트의 목적, 대상 독자, 주요 기능, 시작 방법을 앞부분에서 설명한다.
- 내부 구현 방식보다 독자가 수행할 작업과 확인할 결과를 우선한다.
- README 결과물은 항상 영어로 작성한다. 대화 언어, 원자료 언어, 기존 README 언어를 따라 한국어로 작성하지 않는다. 제목, 본문, 표 설명, 캡션, 대체 텍스트와 요청 예시의 설명도 영어로 쓴다. 명령, 경로, API 식별자와 고유명사는 정확한 원문을 유지한다.
- 사실에 근거해 간결하고 구체적으로 쓴다. 과장된 홍보, 반복 설명, 내용 없는 항목을 제거한다.

## 문체와 제목

- 제목·소제목·본문 전체에 객관적인 문서체를 사용한다. 독자에게 말을 걸거나 질문하고 답하는 대화체는 절대 쓰지 않는다.
- 제목과 소제목은 내용을 식별할 수 있는 명사구로 쓴다. 예: `Overview`, `Skill Selection`, `Usage`, `Requirements`.
- `어떤 스킬을 선택하나요?`, `어떻게 시작하나요?`, `Which skill should you choose?`, `Ready to get started?` 같은 질문형·대화체 제목은 금지한다.
- 본문에도 `Let's get started`, `Want to learn more?` 같은 대화 유도 표현을 넣지 않는다. 필요한 절차는 직접적인 지시문이나 사실 설명으로 쓴다.
- 사용자가 복사해 에이전트에 전달할 요청 예시는 실제 입력 형식으로 제시할 수 있다. 문서의 설명과 제목까지 대화체로 쓰는 근거로 삼지 않는다.

## 소스 확인 범위

소스 코드는 공개 동작을 검증하는 근거다. 매니페스트·패키지 정보, 명령 진입점, `--help`, 공개 예제, 관련 설정과 테스트 등 필요한 범위만 읽고 사용자 관점으로 설명한다.

| 내부 근거 | README에 담을 내용 |
| --- | --- |
| 라우트 처리기, UI 모듈 | 사용자에게 제공하는 작업·기능 |
| 시작 명령, 패키지 스크립트 | 확인된 설치·실행 절차 |
| 공개 메서드 시그니처 | 라이브러리의 호출 가능한 공개 API 예제 |
| 환경 변수 접근 | 사용자가 설정할 이름과 의미 |
| 내부 함수, 클래스 관계 | 일반적으로 생략 |
| 데이터 처리 파이프라인 | 입력, 결과, 한계. 그림은 이해를 돕는 경우에만 포함 |

각 정보가 프로젝트의 **이해·선택·설치·실행·설정·사용**에 도움이 되거나 중요한 안전·호환성 제약을 설명하는지 판단한다. 해당하지 않으면 제외한다.

## 공통 권장 요소

- 프로젝트 이름과 목적을 직접 설명하는 소개.
- 사용자 관점의 결과로 표현한 주요 기능.
- 실행하거나 활용할 수 있는 프로젝트라면 근거가 있는 시작 절차 또는 사용 예제.
- 필요한 환경, 설정과 제약.
- 이해를 실질적으로 돕는 스크린샷, 다이어그램 또는 예제.
- 해당하며 확인된 경우 실제 라이선스와 인용·참고 정보.

현재 프로젝트에 필요한 절만 포함한다. 제목 계층, 언어 태그가 있는 코드 블록, 정확한 상대 경로 링크, 고정 항목 비교용 간결한 표, 설명적인 이미지 대체 텍스트를 사용한다. 장식용 배지와 과도한 중첩 목록은 피한다.

## 점검

1. 명령, 경로, 사전 조건과 예제가 저장소 및 명시한 플랫폼에 맞는지 확인한다. 추론한 명령을 실행 검증한 것으로 표현하지 않는다.
2. 현재 기능, 로드맵, 실험과 검증되지 않은 계획을 구분한다.
3. 이미지 경로가 유효하고 그림이 설명하는 프로젝트와 일치하는지 확인한다.
4. 필수 공개 인터페이스가 아닌 내부 메서드·클래스 이름과 상세 호출 순서를 제거한다.
5. 처음 읽는 사람이 구현 코드를 보지 않고도 수행 가능한 작업을 이해할 수 있는지 확인한다.
6. README의 설명이 영어로 작성되었는지 확인한다.
7. 제목과 본문에서 질문형 제목, 독자에게 말을 거는 표현, 대화체 문장을 제거한다.

## 작업 범위

- README 작성을 코드 문서화, 함수·클래스 목록 또는 구현 분석 보고서로 바꾸지 않는다.
- 일반적인 프로젝트 소개에 비공개 구현 이름을 노출하지 않는다. 공개 API 이름, CLI 플래그와 설정 키는 독자가 사용해야 할 때만 포함한다.
- 설치 명령, 출력 예제, 성능 수치, 호환성 또는 라이선스 조건을 지어내지 않는다.
- `docs/`, `CONTRIBUTING.md`, `CHANGELOG.md` 같은 문서 분리 정책을 강제하지 않는다. 사용자가 요청하지 않은 문서 구조 개편은 범위 밖이다.
- README 내용과 요청된 시각 자료에 집중한다. 허가 없이 코드를 리팩터링하거나 부가 문서를 만들지 않는다.
