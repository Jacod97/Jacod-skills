# 문서 작성 (write-docs)

이 파일은 길잡이다. 규칙 본문은 `references/` 아래에 계층별로 나뉘어 있고, 지금 쓰는 문서에 필요한 파일만 읽는다.

## 계층과 우선순위

```
references/core.md              0층  모든 문서
references/word-rule.md         0층  용어 표기·개조식 종결 (core가 참조)
references/reading-modes.md     1층  읽는 방식 (참조형 / 선형)
references/types/<type>.md      2층  문서 종류
references/modules/<module>.md  가로축  type이 쓰겠다고 정한 기능
assets/                         템플릿·전처리부 원본 (복사해서 씀)
```

- 읽는 순서: core → 읽는 방식 → type → 모듈
- 같은 항목에서 규칙이 부딪치면 위층이 이긴다: type > 읽는 방식 > core
- 모듈은 type 파일의 "모듈" 항목에 적힌 것만 읽는다

## 1. 분류

| type | 요청 신호 | 읽을 파일 |
|---|---|---|
| 연구일지 | 연구일지, 실험 기록, 오늘 실험 정리, 결과 기록 | `types/research-log.md` |
| 리뷰 (설명 문서) | 논문 리뷰, ~ 설명하는 문서 만들어줘, 설명해줘, 이해하고 싶음, 개념 정리(학습 목적) | `types/review.md` |
| 참조 문서 | 데이터셋 정리, 저장소 구조 정리, 라이브러리·도구 조사 | `types/reference.md` |
| 연구계획서 | 연구계획서, 제안서, 연구 아이디어 정리, 실험 계획 | `types/research-plan.md` |

- 신호가 분명하면 묻지 않고 그 type으로 간다.
- 애매하면 AskUserQuestion으로 용도를 한 번 묻는다. 예: "논문 정리해줘"
  - 처음부터 읽으며 이해하는 설명 문서 → 리뷰
  - 나중에 구조·설정·수치를 찾아보는 정리 문서 → 참조 문서
  - 이 논문을 바탕으로 내 연구를 설계하는 문서 → 연구계획서
- 표에 없는 문서 종류면 core와 가장 가까운 읽는 방식만 적용하고, 그 사실을 사용자에게 알린다.

## 2. 규칙 로드

1. `references/core.md`와 `references/word-rule.md`를 끝까지 읽는다.
2. type 파일을 읽는다. 맨 위 "속성"에 읽는 방식, 출력, 합의 방식, 모듈이 있다.
3. `references/reading-modes.md`에서 해당 읽는 방식 절을 읽는다.
4. type 파일의 "모듈" 항목에 적힌 `references/modules/` 파일을 읽는다.
5. 작업 목록 첫 항목에 적용 규칙을 적는다. 예: "core + 선형 + 리뷰 / 모듈: 원자료 수집, LaTeX, 그림 제작, 독자 검토"

## 3. 절차

1. 분류
2. 규칙 로드
3. 원자료 수집 (type이 쓰는 경우)
4. 합의: type의 사전 단계(있으면) → core의 구성안 협의. 에이전트가 장·절마다 설명 내용과 흐름을 적은 구성안을 제안하고, 사용자가 승인하거나 흐름을 제안함. 승인 전에는 어떤 파일도 만들지 않음
5. 작성
6. 검증: core 점검 + type 점검 + 사용한 모듈의 점검
7. 전달: 결과 파일과 함께, 계산으로 얻은 값과 확인하지 못한 값을 따로 밝힘

원자료를 기다리는 동안 할 수 있는 일(개념 목록, 구성안 초안)은 먼저 한다.

## 새 type·모듈 추가

- 새 문서 종류는 `references/types/`에 파일 하나로 추가하고, 위 분류 표에 한 줄을 더한다. type 파일은 속성 + 합의 + 고유 규칙 + 점검만 갖는다.
- 둘 이상의 type이 같은 규칙을 갖게 되면 core나 모듈로 올린다.
- 사용자가 직접 지적한 문제 중 일반적인 것은 해당 계층의 규칙으로 추가하자고 제안한다.
