# 구현 규칙

## 범위

- task 문서에 적힌 것만 구현한다. 적히지 않은 기능·리팩터링·정리를 하지 않는다.
- 결정이 필요한 상황을 만나면 직접 정하지 않는다. "계획과 맞지 않을 때"를 따른다.

## 계획과 맞지 않을 때

- task 문서의 대안에 해당하면 대안대로 하고 DLFA에 기록한다.
- 대안에 없으면 멈추고 보고한다: 무엇이 계획과 다른지, 원인(모르면 "미확인"), 가능한 방법. 즉석에서 다른 길로 가지 않는다.

## 기존 구조

- config에서 값이 흘러오는 구조를 따른다. 모듈 내부에 변수·기본값을 만들어 config 값을 덮어쓰지 않는다.
- 디렉토리 간 의존 방향과 모듈 분리를 지킨다. 스크립트식으로 한 곳에 몰아 쓰지 않는다.
- 빌드 모드는 `planning-output.md`의 의존 관계·API를 기준으로 한다.

## 예외처리

- task 문서의 예외처리 사항 중 승인 칸이 "승인"인 행만 그대로 구현한다. 비어 있거나 "거부"면 처리하지 않는다.
- 그 외에는 `try/except`, 넓은 `except`, `dict.get(key, default)`, `getattr(..., None)`, `hasattr` 분기, 누락 시 `continue`, 조용한 기본값 대입으로 에러를 숨기지 않는다.
- 터지게 두거나, 원인 파악에 필요한 맥락(파일 경로, 키, 인덱스 등)을 담아 `raise`한다.
- 구현 중 예외처리가 필요해 보이면 넣지 말고, task 문서 예외처리 사항에 행을 추가(승인 칸 비움)한 뒤 멈추고 보고한다.
- 실행 중 에러를 만나면 증상을 막는 수정이 아니라 원인을 조사해 보고한다.

## 이름

- 줄임말을 쓰지 않는다. 의미가 드러나는 풀네임을 쓴다.
- planning 문서에 적힌 파일·함수·클래스 이름은 그대로 쓴다.
- 문서·주석에 합의 안 된 용어·약어를 만들어 쓰지 않는다.

## 점검 (끝내기 전 diff를 다시 읽는다)

- task에 없는 변경이 없는가
- 승인 안 된 예외처리 패턴이 새로 들어가지 않았는가
- config를 우회하는 하드코딩이 없는가
- 줄임말 이름이 없는가
- 의존 방향을 어기지 않았는가
- 계획과 다른 점이 모두 DLFA에 기록됐는가
